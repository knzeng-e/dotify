# Dotify 1.3.0 — pilot release candidate

Status: prepared from `dev` through PR #212; publish only after the PR is merged
and the final merge commit passes every required check.

## What this release delivers

Dotify 1.3.0 turns the current development line into one coherent pilot
candidate for ordinary web and Product DevNet. The release centers shared
musical presence: listeners can enter a room from a link without a wallet,
follow the host's live track while browsing, talk and react without losing the
player, and understand artist access and support in human language.

The production spine now keeps uploads and content keys server-side, binds key
requests to signed sessions and canonical releases, serves a cached catalog,
uses versioned key custody, and exposes deterministic readiness evidence. The
Product build includes app-scoped identity, Product-signed key requests, an
explicit CDM adapter boundary, native payment proof links, payer-address
visibility, royalty recovery, and optional artist gifts without claiming that
Product CDM writes or CASH settlement are broadly proven.

Playback and room work includes synchronized seek/pause state, uninterrupted
track handoff for room listeners, bounded Next and Previous preparation, DAV2
startup improvements, off-thread decryption, mobile keyboard stability, a
persistent room-aware player dock, collaborative requests and host lineup, and
clear reconnect states. The visual system, catalog, player, artist workspace,
and room layouts have been consolidated for mobile and desktop.

## Release review fixes

- TURN credentials require a short-lived HMAC capability issued only to the
  current room host or a joined listener. Anonymous callers receive no relay
  credential.
- DAV2 range reads remain on compatible Pinata gateways, while the bounded
  full-file recovery path can fail over to independently operated IPFS
  gateways.
- Product executable `appVersion` is `[0, 1, 28]` so hosts can refresh the
  changed playback and room behavior.

## Operational changes

Deploy signaling and API with one new shared secret before relying on TURN:

- `SIGNAL_TURN_CAPABILITY_SECRET` on `dotify-signal`;
- `TURN_CAPABILITY_SECRET` on `dotify-api` with the exact same 32+ character
  random value;
- keep this value distinct from `TURN_REST_SECRET`;
- `SIGNAL_TURN_CAPABILITY_TTL_MS` defaults to 120 seconds and is tracked as
  `120000` in the Fly signaling configuration.

Deploy or restart signaling and API together, then publish the Netlify and
Product bundles. A secret mismatch fails closed for TURN and leaves direct/STUN
room connections available. No database migration or release-time contract
migration is required.

prepares the candidate; it does not by itself prove a public pilot. The last
published Product CDM validation identity remains app `[0, 1, 27]` at CID

Before publishing the GitHub release and calling the pilot ready:

1. Record the final PR merge SHA and green CI checks.
2. Configure the paired TURN capability secrets and smoke an anonymous denial
   plus an authorized host/listener grant.
3. Publish Product app `[0, 1, 28]`, record its CID, and recapture
   candidate-bound Product payment/access and room evidence.
4. Run the W13 readiness command with the candidate artifacts.
5. Exercise first sound and room recovery on supported physical devices,
   including the known iPhone path.
6. Rehearse rollback and confirm retained content-key versions still open
   existing releases.

Until those live gates pass, mark the release as a prerelease or hold it as a
draft. Do not infer Product Mobile in-app WebRTC, Product CASH settlement,
Human-free personhood, or large-room scale from local and CI evidence.

## Rollback

The code rollback target is the pre-release `main` commit
`6ee2dc9c4c206ecb4583ff3c3457315af5022abc`. Product rollback must republish the
last known-good CID and app version; API and signaling rollback must restore a
compatible pair. Do not remove retained content-key secrets during rollback.

After merge, create GitHub tag `1.3.0` on the verified merge commit and use this
document as the curated release body. If the live W13 gates are incomplete,
publish it as a prerelease rather than a stable release.

The live Product Web gateway was reproduced with an older published bundle. A
shared-room arrival attempted Product CDM setup immediately and the host
reported `Malformed protocol error payload: expected 3 bytes, received 6`;
passive rendering also opened the direct EVM RPC. Those failures could obscure
the room experience even though room discovery and catalog API reads do not
need an authoritative chain read.

The candidate now creates the Product CDM reader only when a protected access,
runtime, payment-readback, or artist-runtime read is actually requested. A
failed host setup rejects that read and clears the cached setup promise so a
later explicit retry can recover; it never falls back to viem. Product DevNet's
chain identity and PAS display asset are resolved locally during initial
render. Artist-runtime discovery is deferred until a connected user opens the
account or artist surface.

## Result and decisions

W11 adds a read-only Product DevNet journey harness instead of hiding the
remaining live Product gates inside prose. The harness validates the local
Product build contract: current SDK/tool pins, Product DevNet chain ID and CDM
registry, DotNS domain, canonical public URL, API and signaling origins, gateway
configuration, empty browser secrets, generated CDM package addresses, deploy
CLI pin, and the fact that the tracked Product profile still defaults to the
viem runtime adapter until Product CDM writes are live-proven.

The same command can consume two live evidence exports:

- the existing browser-side Product CDM host smoke JSON after a funded Product
  host account signs and submits a Classic unlock;
- a deliberately small room JSON that records a Product host sharing a
  canonical `https://dotify-test01.dev-dot.li/#/rooms/<code>` link and an
  ordinary browser guest joining without an account and hearing audio.

Missing live inputs are reported as `blocked` or `not-run`, never as passed.
Payment submission, confirmation, and access verification remain separate
states. The harness exits non-zero only when static config or supplied evidence
is unsafe/inconsistent, so it can run in CI or local release prep without
requiring funds, private keys, or Product host approval prompts.

The PR #153 review follow-up hardened the harness in four places:

- Product CDM smoke evidence is no longer trusted from derived `checks` rows or
  `summary.tone`. The harness validates captured time, current build SHA,
  Product app version, public app URL, CDM registry, Product host account
  context, explicit host approval, native payment/readback events, backend key
  release, and same-identity continuity.
- Product Desktop and Product Web gateway evidence are separate claims. Room
  evidence must name `hostSurface`, `hostOrigin`, `hostVersion`, and
  `guestOrigin`; Product Desktop evidence leaves Product Web as `not-run`.
- `VITE_ETH_RPC_URL` must be one of the known Product DevNet Asset Hub RPC
  endpoints instead of any HTTPS URL.
- The recorded build commit now comes from `git rev-parse HEAD`, so linked Git
  worktrees resolve their real `HEAD` instead of falling back to `unknown`.

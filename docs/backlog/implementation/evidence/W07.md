## Result and decisions

W07 replaces the single implicit content-key secret model with an explicit
versioned key vault. New backend uploads use the active
`dotify-content-key-vN` version and write refs shaped like
`dotify:enc:v2:key-vN:ipfs://<CID>`. Legacy refs still resolve through v1, and
the default release-bound path stays v2 unless an operator configures a newer
active version.

The migration path is additive: old releases remain readable only while their
exact version secret is retained. Missing key versions, invalid scopes, wrong
release identity, and Free-to-protected policy changes fail closed and never
fall back to another secret. The docs now state the important boundary: key
grants are short-lived, but a derived AES key already delivered to a client is
not made unknown by rotating config.

The implemented rehearsal is deliberately synthetic. It creates a local backup
with fake v1/v2/v3 secrets, restores an isolated key service from that backup,
decrypts legacy ciphertext after adding v3, proves v3 ciphertext does not
decrypt with the old v2 release-bound key, and verifies that denied Free access
does not derive or disclose a key.

Artist export and alternative-operator recovery remain follow-up scope. They
need artist authentication, encrypted key export, and authority-continuity
checks before Dotify can claim artist-sovereign recovery without the current
backend operator.

## Compatibility and operations

- Supported devices, browsers, and Product host versions: ordinary web remains
  on the viem-backed path; Product DevNet appVersion is bumped to `[0, 1, 18]`
  so republished Product bundles understand `dotify:enc:v2:key-vN` refs.
- New config/permissions and documented defaults:
  `CONTENT_KEY_MASTER_SECRET` remains the v1/v2 compatibility secret;
  `CONTENT_KEY_MASTER_SECRETS` optionally retains explicit version secrets;
  `CONTENT_KEY_ACTIVE_VERSION` selects the version for new uploads and defaults
  to `dotify-content-key-v2`.
- Storage/key/contract migration and compatibility evidence: legacy v1
  ciphertext decrypted after adding active v3; new v3 ciphertext failed with
  the old v2 release-bound key; upload route test verified new v3 refs.
- Deployment identifiers: not deployed in this sequence.
- Rollback procedure and rehearsal evidence: unset
  `CONTENT_KEY_ACTIVE_VERSION` and keep the existing v1/v2 compatibility secret
  to return new uploads to v2. Do not remove any retained version secret needed
  by already published ciphertext. Synthetic backup/restore rehearsal passed.
- Data collected, retention, and user controls: no production keys, user data,
  or real audio artifacts were written. The rehearsal writes fake secrets under
  `/tmp`/macOS temp only.

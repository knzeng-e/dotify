## Result and decisions

W09 hardens the existing peer-to-peer room spine instead of starting an SFU
migration. The current pilot cap remains conservative, and public room metadata
now exposes `maxListeners` and `isFull` so guests see a full room before
attempting to enter. The signaling server still enforces the cap on `room:join`.

The browser now installs `window.__DOTIFY_ROOM_QUALITY__` for QA. The bounded
page-local snapshot records room phases such as create, join, rejoin, ICE server
resolution, offer/answer, stream-ready, remote-audio cue, peer connected,
disconnect, failure, retry, timeout, and host reconnect/online. For connected
peers it summarizes browser WebRTC stats when available: relay/direct candidate
type, round-trip time, jitter, packet counters, byte counters, and outgoing
bitrate. It does not store SDP, ICE candidate strings, IP addresses, audio
source references, content keys, wallet identifiers, or listening history.

Host resource cleanup is stricter during signaling interruption: a hosting page
closes existing peer connections when its room transport disconnects, then uses
the existing host resume token path to receive fresh `listener:ready` events and
send new offers. Listener reconnect also discards stale peer state before
rejoining with a fresh socket. Retry remains bounded by the existing single
automatic retry.

The Product iOS pre-ICE boundary remains explicit. If `RTCPeerConnection` is
missing in the Product host webview, Dotify does not label this native in-app
audio; it routes the canonical room URL to the external browser.

No guest key/file path, hidden fallback signer, unconditional SFU migration,
global listener-cap increase, permanent analytics, or unsupported host handoff
was introduced.

## Result and decisions

W03 replaces process-local `contentHash -> runtime` key lookup with canonical
release-bound key delivery. Catalog-backed encrypted tracks now send a release
identity with key requests: `releaseId`, runtime address, artist address,
`audioRef`, and `keyVersion`. The backend treats those fields as claims to
verify against the fresh confirmed catalog read model, `ArtistDirectory`, and
the current target runtime track state before it calls `musicAccCanAccess` or
derives a key.

New backend uploads use release-bound content key v2:

```txt
dotify-content-key-v2:<chainId>:<runtimeAddress>:<contentHash>
```

and return:

```txt
dotify:enc:v2:key-v2:ipfs://<CID>
```

The upload response also returns the runtime address used for encryption. The
artist console retains that runtime through the eager upload flow and, at final
publication, compares it with the current publication runtime. If the artist
account/runtime changed after the eager upload, Dotify clears the stale upload
and retries from the raw audio bytes. If the browser no longer has those bytes,
publication fails closed instead of registering ciphertext under a runtime that
cannot later derive its key.

Legacy encrypted refs remain supported with the old v1 `contentHash` scope when
the fresh catalog snapshot has exactly one encrypted release for that hash. If
multiple runtimes claim the same legacy hash, Dotify refuses key delivery even
with an explicit release identity because the v1 key bytes cannot distinguish
the releases. Stale catalog evidence, identity drift, inactive releases, and
unsupported key versions all fail closed.

No contracts or stored media were migrated. This PR changes API/web key
request semantics, upload encryption scope for future server-encrypted uploads,
tests, and operator/security documentation.

## PR review follow-up

Automated review on PR #142 raised two valid issues:

- `web/src/hooks/useCatalog.ts` cached content keys by `contentHash` only. That
  is correct for legacy v1 keys, but wrong for release-bound v2 keys because two
  runtimes can share the same raw hash while deriving different v2 keys. The
  fix adds `contentKeyCacheKey()`: legacy/no-release requests keep the old
  hash-only key, while v2 release-backed requests include key version, runtime,
  release ID, content hash, and `audioRef`. `useCatalog.cache.test.ts` locks the
  behavior.
- `services/api/src/routes/uploads.ts` encrypted eager audio uploads for the
  runtime tied to the upload authorization, while final publication could later
  use a different artist runtime if the connected account changed. The fix makes
  `/api/uploads/audio` return the encryption runtime, makes the frontend retain
  that structured upload result, and revalidates it against the publication
  runtime before `registerRights`. Mismatches retry from raw audio when possible
  and otherwise fail closed with an artist-readable error.

  hash match. New backend uploads write the `key-v2` audio ref and include
  `keyVersion` in manifests.

  rolling forward or back. Rolling back only the API can make new `key-v2`
  uploads undecryptable; rolling back only the web can omit release identity
  for modern requests. Rehearsal not run.
- Data collected, retention, and user controls: key requests now include public
  release identity fields already visible in catalog/on-chain state. No content
  keys, signatures, nonces, sessions, or raw media are persisted by this change.

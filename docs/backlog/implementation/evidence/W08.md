## 2026-09-19 first-chunk sizing follow-up

- Scope: partial #88 delivery; reduce the encrypted range required before a
  newly published protected track can append its first audio bytes.
- Starting dev SHA: `e63470467adaa788efab75c97b6edeaef8c7d721`.
- Implementation SHA actually tested:
  `d1151bcd46388c73c2a85b53840c686002657ba1`.
- Branch: `perf/dav2-first-chunk`; PR #200
  (`https://github.com/knzeng-e/dotify/pull/200`).
- Code readiness: locally verified. Release readiness: not deployed; no live
  Product host, physical device, Pinata upload, or gateway timing is claimed.

New server-encrypted DAV2 publications use a 256 KiB baseline first clear chunk
followed by the existing 512 KiB steady-state chunk size. For MP3 files, the
validated ID3-to-audio offset is passed to the encryptor: when leading metadata
would crowd audio out of the baseline, the first chunk expands only enough to
retain up to 64 KiB of audio payload and never exceeds the former 512 KiB
boundary. An ordinary first encrypted range is therefore 262,160 bytes
including its AES-GCM tag instead of 524,304 bytes, almost exactly half, while
a large embedded cover cannot silently turn the prefetched range into metadata
only. The authenticated header already carries each chunk's exact clear and
encrypted lengths, and browser playback already calculates offsets from that
table, so no schema, audio ref, key version, contract, or existing object
changes.

The API keeps an explicit `chunkSize` option uniform for compatibility with
fixtures and recovery tooling; callers may deliberately supply a smaller
`firstChunkSize`. Both API and browser parsers now reject a declared clear
chunk larger than the header's steady-state maximum. Existing Dotify-produced
containers satisfy that invariant and remain byte-compatible.

The music catalogue, artist profile, and room-creation picker now treat hover,
keyboard focus, touch/pointer-down, and a chosen room track as deliberate intent
to warm only the public encrypted DAV2 header and first chunk. The flow imports
no wallet, runtime, access, session, key-service, decryption, or playback code.
Locked releases therefore remain locked, and room guests retain the same
walletless stream-only boundary.

Exact ranges are shared while a speculative request is in flight and retained
in a session-only LRU for at most 90 seconds. The cache is limited to 8 entries
and 3 MiB, accepts at most a 256 KiB header and a 768 KiB first chunk, cancels a
stale different-track intent, and lets real playback retry normally if
speculation was cancelled or failed. DAV2 startup metrics now set
`intentPrefetched` so cold and warm samples can be compared without confusing
this byte cache with the existing winning-gateway cache.

## Result and decisions

W08 ships a bounded first-sound observability and recovery slice on top of the
existing DAV2 startup hardening already present on `dev`.

The app now installs `window.__DOTIFY_AUDIO_STARTUP__` for QA. The snapshot keeps
bounded DAV2 startup events and host source-to-first-audio events in memory, so
reviewers can inspect key authorization, gateway selection, first bytes,
decryption, MSE append, fallback/error, and actual media start without reading
console logs. The snapshot stores timings, refs, CIDs, gateway URLs, and phase
metadata only; it does not expose content keys or decrypted media.

The catalog hook now maps DAV2 phases to short player/dock labels while audio is
preparing: access confirmation, gateway lookup, first bytes, first sound prep,
fallback, and unavailable states. Unauthorized access still fails closed to the
access gate with no preview source and no listener key request.

Cover artwork now uses a shared fallback generator and a 1.2 second per-gateway
budget. If gateway sources fail or time out, the UI renders deterministic Dotify
artwork seeded by the track/release title instead of leaving broken image
surfaces. This treats cover work as a linked #87 slice without claiming the whole
responsive cover pipeline is complete.

PR review follow-up tightened two W08 edges: lazy cover images now arm their
gateway timeout only once the image enters browser load range, and player/dock
startup labels now surface while playback is still idle and the protected source
is resolving.

No backend read-through gateway, CDN purchase, playback-engine rewrite, preview
system, contract change, or production secret change was introduced.

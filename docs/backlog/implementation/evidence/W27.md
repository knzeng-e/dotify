## Result and decisions

`useSession` now consumes a typed `RoomRealtimePort` instead of an unrestricted
Socket.IO client. The adapter retains connection events, reliable/volatile
emits and bounded acknowledgements. Ack snapshots run synchronously before
subsequent live events; a regression test protects this packet ordering.
Listener rejoin now has the same 8-second
acknowledgement bound as other room requests; an absent reply shows recovery
instead of waiting forever. WebRTC peer ownership and all access checks remain
in their existing modules.

`VITE_DOTIFY_ROOM_REALTIME=observe` subscribes in a Product container while a
room is joined. `dual` also publishes host aggregate presence every 10 seconds
with a 30-second TTL. Neither mode applies Celerity data to visible room state.
Guests never publish or request an account to join. SDK Host mode uses the
sponsored allowance; its signature is not Dotify host authentication.

The strict schema refuses private and unsupported payloads. Room/channel,
versions, IDs, sequences and both expiries are checked before bounded replay
tracking. SDK encoding enforces byte size; local reservations leave room for
one discovery beacon and survive uncertain submits until expiry. Other tabs
and allowance consumers remain outside this local budget view.

The observer is isolated from the room port and state setters. Initialization,
subscription and publication failure cannot stop audio or grant authority.
It disposes late clients, stops on an 8-second deadline or interruption, never
overlaps an uncertain write, and records publisher self-echo separately.
An already-issued Host operation cannot be canceled by this timeout.

The [per-event decision matrix](../../../explanation/room-realtime-transports.md)
retains Socket.IO for all authoritative responsibilities. Existing beacon
discovery is hybrid. No private chat or signaling is published; encryption is
therefore not installed as an unused production key system. The offline
experiment exercises ephemeral X25519/AES-GCM/deflate fragmentation with real
SDK encoding, and explicitly lacks authenticated peer key agreement.

Host 0.19.1 ChatManager can register rooms/bots, send messages and subscribe
to actions. Invitations and Join buttons are future Host-surface candidates;
scheduling, consent and real delivery are unverified. No messages are sent.

## Compatibility and operations

- Ordinary web keeps Socket.IO; Product builds are compiled, not live-verified.
- Tracked `.env.product-devnet` explicitly sets the new flag off; unknown
  values and enabled observation without Product mode fail production checks.
- No server, secret, data migration, contract or access-policy change.
- No deployed CID or new release version. Build SHA/version in diagnostics
  must be paired with the actual deployed CID in a later operator capture.
- Diagnostics: last 200 events in memory, no room/producer/account IDs or
  payloads. Clear with `window.__DOTIFY_ROOM_REALTIME__.clear()`; reload also
  clears them. Age/gaps are not verified latency/loss; SDK callbacks suppress
  duplicates before the application sees them.
- Dual publication exposes room code/count to public gossip. Random producers
  do not remove sponsored-account or room-code correlation.
- Rollback: flag off and rebuild, then reload/leave active sessions. Existing
  statements expire after their TTL; delayed Host submits remain possible.
  The default build and disabled-mode tests verify the local rollback boundary.

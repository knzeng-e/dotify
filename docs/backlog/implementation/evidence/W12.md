## Result and decisions

Artists now get a clearer publication review before signing. The review names
the controller wallet, artist runtime, access condition, total support amount,
network-fee boundary, public archive choice, catalog visibility boundary, and
recipient value flow including artist remainder. Uploads alone are explicitly
not treated as publication, and transaction submission alone is not treated as a
completed release.

The registration path now reports a four-step roadmap: protected assets, rights
manifest, runtime registration, and catalog read-back. Successful publication is
shown only after the registration transaction is accepted and Dotify can read
the release back from the catalog. If uploads fail, signing is rejected, the
registration transaction fails, or the catalog index is delayed, the modal keeps
the draft recoverable and names what was or was not published.

Listener support uses the same transaction fact model. Classic receipts now
show amount, acquired access, recipient count, settlement state, and network-fee
boundary across standalone and Product-domain states. Confirmed support,
included-but-unverified payments, canceled wallet actions, and generic failures
are distinct user-facing states.

The shared `TransactionModal` gained a compact fact table so receipts can carry
plain-language verification facts without forcing a blockchain tutorial. The
change does not add a new payment rail, subscription model, passkey route,
frontend secret, hidden signer, contract migration, or live deployment claim.

`docs/operations/artist-support-facilitator-script.md` records a short pilot
script for asking artists whether control is understandable and listeners who
they believe benefited. It explicitly forbids recording real answers without an
authorized participant session.

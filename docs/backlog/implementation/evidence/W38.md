# W38: bounded music contracts and paged catalogs

## Decision and scope

Implemented from tested `dev` commit `bd813f7e49183900a5970f665e4f18e74abd674d`.
On 2026-10-28 the owner confirmed that internal runtimes will be replaced from
scratch. This is a single new contract generation, with no runtime-version probe,
legacy pagination fallback, old-facet fixture or live migration.

No contract was deployed or upgraded. Activate API and clients with the fresh
factory/runtime deployment, not independently against the existing deployment.
Future upgrades remain artist-authorized; a local replacement rehearsal verifies
that the current generation preserves purchases, NFT ownership and royalty data.

## Contract boundaries

| Value | Maximum | Meaning |
| --- | --- | --- |
| Title | 800 UTF-8 bytes | Supports up to 200 four-byte characters |
| Artist name | 800 UTF-8 bytes | Same publishing envelope as title |
| Description | 8,000 UTF-8 bytes | Matches existing metadata-edit ceiling |
| Each image/audio/metadata/rights reference | 512 UTF-8 bytes | Bounded on-chain locator |
| Royalty recipients | 16 entries | Includes the primary artist when their share is positive |
| Hash page | 100 hashes | Registration order, including inactive tracks |

Registration retains its existing nonempty requirements and access validation.
Edits use the same limits; an empty edited description remains allowed.
Duplicates count toward the recipient limit because every entry performs a
settlement step. Splits are never silently truncated. The UI rejects an excessive
split count before uploading/signing. The factory installs the page selector from
creation. No storage slot, struct field, field ordering or payment rule changes.
`LibMusicBounds` contains constants only and adds no Diamond storage.

`musicRegTrackHashesPage(offset, limit)` returns an empty page at/beyond the end
or for zero limit, clamps large limits to 100, and subtracts before adding to avoid
overflow. Existing single-index reads remain useful to audit/export tooling; the
catalog API and both Web/Product runtime readers enumerate with pages directly.
For 205 tracks, hash enumeration takes one count plus three page calls, rather
than one count plus 205 single-index calls. Record reads remain necessary.

## Failure and trust boundaries

The API pins count, pages and records to the same confirmed checkpoint. Missing,
short or failing page responses fail the indexing operation; they do not trigger
an old-protocol fallback. Client readers also reject incomplete pages.

Artists own their Diamonds and could install arbitrary code. The indexer therefore
checks the same byte/split ceilings even for the new generation. It rejects large
split counts before issuing split-entry RPCs. A deterministic bounds violation
excludes only that release; its ID/reason is persisted in `excludedReleases`, and
catalog metadata reports a nonzero `excludedReleaseCount`. Corrections restore it
on the next event/reconciliation. Exclusions affect the content revision/ETag.
RPC/decoding/storage failures are not exclusions and cannot advance a checkpoint.
No metadata truncation invents an alternative rights distribution. Catalog data
remains non-authoritative for payment or content-key access.

These checks bound accepted content and split enumeration, not the byte size of
an arbitrary malicious RPC response before decoding. They are not an RPC-provider
rate limit or a solution for permissionless creation of empty runtimes.

## Validation

- 90 Hardhat tests pass, including 12 W38 cases: every exact byte boundary and
  one byte over (multibyte text), recipient cap, empty/oversized page edges,
  unauthorized module replacement and preservation of paid access/NFT/splits.
- All active fixture facet selectors are unique; the factory/audit tests verify
  the added selector. Storage definitions were inspected unchanged; the module
  replacement rehearsal exercises the existing namespaced state.
- At 16 recipients, a local EVM purchase used **694,398 gas** for new EOA recipients
  and **2,329,153 gas** for recipients consuming their 100,000-gas payout budget.
  Both grant access; failed transfers remain claimable. These figures are local
  solc/Hardhat evidence, not PolkaVM weight estimates or production fee promises.
- 233 API tests pass, including page batching, checkpoint pinning, no fallback on
  errors, exclusion/restoration, persisted reasons and unchanged checkpoint on RPC failure.
- 1,040 frontend unit tests pass, including both runtime adapters and the recipient
  cap. A subsequent focused run passes 31 adapter tests, including two added
  incomplete-page rejection checks. Web build, API typecheck and contract formatting checked separately.
- Generated viem and Product CDM bindings were regenerated. CDM regeneration also
  picks up existing contribution custom errors previously absent from its merged ABI.

## Fresh activation and later upgrades

1. Compile the new facets/factory and rehearse the repository's fresh deployment
   procedure with the intended native network/compiler. No old-runtime migration.
2. On authorized reset, deploy the fresh generation and update recorded addresses,
   finalized CDM versions, manifests/bootstrap and API directory identity together.
3. Validate registration at the limits, paged discovery, a Classic purchase and a
   failed-recipient claim through Product Desktop/mobile and ordinary Web.
4. Release the matching API and clients. A client-only rollout against old runtimes
   is unsupported. Keep a coordinated deployment record for rollback.

Before real users, retain a future-upgrade procedure: owner inspects current loupe
routes, storage compatibility and audited code, signs an atomic `diamondCut`, then
checks existing rights and purchases. Replace existing selectors; Add only genuinely
new selectors. Never replace the Diamond address or reinitialize its stored state.
The current rehearsal proves this foundation without carrying an old deployment path.
